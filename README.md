# 企业知识库助手（作品 A）

一个可评估、可引用、可部署的 RAG 问答系统。目标不是"能聊"，而是**回答有据可查、效果可量化**。

## 架构

```
文档(PDF/DOCX/MD)
      │
      ▼
  解析 → 切片（带 doc/page/section 元数据）
      │
      ├──► Embedding ──► Qdrant（向量检索）
      │
      └──► 分词 ──────► BM25（关键词检索）
                            │
                        RRF 融合
                            │
                       重排（可选）
                            │
                    LLM 生成 + 引用 [n]
                            │
                  评估集 / Streamlit UI
```

## 快速开始

```bash
# 0. 离线自检（不需要 API Key，验证解析/切片/BM25 是否正常）
python -m ka.cli selftest

# 1. 环境
python -m venv .venv && .venv\Scripts\activate     # Windows
pip install -r requirements.txt

# 2. 配置
copy .env.example .env        # 填入 API_BASE / API_KEY / EMBED_MODEL

# 3.（可选）启动向量库；不装 Docker 也能跑，
#    VECTOR_BACKEND=auto 会自动退回本地文件索引 .index/vectors.json
docker compose up -d qdrant

# 4. 建索引（把文档放进 data/raw/）
python -m ka.cli ingest --recreate

# 5. 提问
python -m ka.cli ask "一线城市住宿标准是多少？"

# 6. 评估
python -m ka.cli eval

# 7. 界面
streamlit run app/streamlit_app.py
```

> **注意**：DeepSeek 官方 API 没有 embedding 接口。要么用硅基流动（一个 Key 同时提供 chat 与 `BAAI/bge-m3`），
> 要么把 `EMBED_MODEL` 换成其他服务商，或改用本地 `sentence-transformers`。

## 目录结构

```
ka/
  config.py     配置（.env）
  llm.py        模型调用：重试、退避、token 统计
  ingest.py     解析、切片、分词
  store.py      Qdrant(REST) + BM25
  vector.py     向量后端选择：Qdrant / 本地文件（auto 探测）
  retrieve.py   混合检索 + RRF + 重排
  answer.py     提示词与引用解析
  eval.py       评估指标与报告
  cli.py        命令行
app/            Streamlit 界面
data/raw/       待入库文档
data/eval/      评估集
tests/          单元测试（不依赖模型）
```

## 评估结果

语料：21 篇制度文档 / 83 个切片；评估集：34 条（含 4 条陷阱题、6 条近义条款辨析）。

| 检索模式 | recall@5 | MRR | 要点覆盖 | 通过率 | 拒答准确 | 过度拒答 |
|---|---|---|---|---|---|---|
| bm25（纯关键词） | 0.967 | 0.933 | 0.950 | 0.941 | 1.00 | **1** |
| vector（纯向量） | 1.000 | 0.967 | 0.983 | **0.971** | 1.00 | 0 |
| hybrid（RRF 融合） | 1.000 | 0.967 | 0.983 | **0.971** | 1.00 | 0 |

**结论（由数据推出，不是拍脑袋）**：

1. 向量检索在词面不匹配的查询上不可替代——「机票买什么舱位」只有它命中（文档原句是“飞行需选择经济舱”）；
2. 但纯向量在“资料无答案”时更容易硬答，因此在生成前加了**相关性闸门**（`MIN_SCORE`），低于阈值直接拒答；
3. **RRF 融合相对纯向量没有可观测增益**（0.971 vs 0.971），且多一层复杂度。当前规模下推荐 vector，保留 hybrid 仅作为编码类查询的备选；
4. 影响最大的一步不是调检索，而是把评分从“LLM 裁判”换成“确定性要点覆盖”——指标方差归零后，改进才可度量。

指标定义：`recall@k` 目标文档是否召回；`MRR` 正确文档的平均倒数排名；`coverage` 回答覆盖了 must_include 要点的比例；`通过率` 综合判定（召回 + 覆盖 + 无禁词 + 拒答正确）。

## 设计取舍

1. **为什么混合检索**：纯向量在编号、专有名词上失准；纯 BM25 不懂同义改述。RRF 只依赖排名，不用调分数权重。
2. **为什么要相关性闸门**：实测纯向量在 4 条陷阱题上硬答了 2 条；在生成前按相似度拦一道，比在提示词里反复强调“不知道就说不知道”更可靠。
3. **为什么切片带章节**：引用要能落到"哪份文档、第几页、哪一节"，否则用户无法验证。
4. **为什么评估不交给 LLM 裁判**：同一份回答在不同模式下被判 4/5 分波动，一条题的波动就能改变整体结论；确定性指标让同样的输入永远得到同样的分数。
5. **为什么用 REST 直连 Qdrant**：少一层 SDK，接口行为透明，便于排查。

## 已知问题（badcase）

> 面试时这部分比指标更重要——它证明你知道系统在哪里坏。

- **词面鸿沟**：问题用“机票”，文档写“飞行/经济舱”，BM25 直接漏召回；这类查询必须靠向量或查询改写；
- **长句漏条件**：模型引用“培训费用超 1 万元需签服务期”时会漏掉后半句“服务期不少于 12 个月”，加“数字必须原样写出”的约束后明显改善，但仍偶发；
- 表格与扫描件解析质量差，“表格型事实”（住宿标准）召回不稳；
- 多跳问题（“我这种情况能报多少”）需要先澄清再检索，当前不支持。
